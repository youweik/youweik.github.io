作者注：这份教程不是 README 的翻译，而是我通读了 Spec Kit 的全部源码、模板文件、命令定义和方法论文档后，用自己的理解重新组织的。重点讲清楚"为什么这样设计"和"实际怎么用"。

一、先搞清楚一个问题：Spec Kit 到底解决什么痛点？

你有没有过这样的经历：

  • • 让 AI 帮你写一个功能，它一口气全写完了，结果发现理解偏了你的意思
  • • 你说"加个登录功能"，AI 直接蹦出 jwt、bcrypt、Redis session，但其实你只是想要一个简单的本地验证
  • • AI 写完代码后，改需求就像推倒重来，牵一发动全身

Spec Kit 的核心洞察是：大多数人把 AI 当打字机用——说出需求，等代码出来。但真正高效的方式是先花时间把"做什么"想清楚、写清楚，再让 AI 按照这份精确的说明书去写代码。

这不是什么新概念——传统软件工程里的 PRD（产品需求文档）、技术方案评审一直在做这件事。但以前写文档又慢又痛苦，没人愿意干。Spec Kit 的思路是：让 AI 帮你写文档，而且这份文档足够精确，可以直接驱动代码生成。

二、核心理念：翻转代码和规格的关系

传统开发：

需求（脑子里） → 直接写代码 → 代码就是真相

Spec Kit 推动的规格驱动开发（SDD）：

需求（脑子里）→ 规格说明（写清楚）→ 实施计划（技术方案）→ 任务拆解 → 代码生成

关键区别：代码不再是第一产物，规格说明才是。代码只是规格的一种"表达形式"。

这意味着：

  • • 改需求 = 改规格说明，而不是改代码
  • • 换技术栈 = 从同一份规格重新生成，而不是重写
  • • 质量保证 = 在规格阶段就卡住问题，而不是写完代码再测

三、安装和初始化

安装

最简单的方式，不需要预装任何东西（只要有 Python）：

# 直接用，不安装
uvx --from git+https://github.com/github/spec-kit.git specify init my-project

如果想持久安装：

pipx install git+https://github.com/github/spec-kit.git
# 之后直接用
specify init my-project

初始化项目

# 指定你用的 AI 编程助手
specify init my-project --integration claude

# 在已有项目目录中初始化
specify init . --here --integration claude

# 其他支持的助手：copilot, gemini, cursor-agent, windsurf, roo 等等
specify init my-project --integration copilot

初始化后发生了什么？

这个命令不只是建了个目录。它做了这几件事：

  1. 1. 创建了 .specify/ 配置目录，记录你选的 AI 助手
  2. 2. 在你的 AI 助手目录（比如 .claude/commands/）下安装了一组斜杠命令（slash commands）
  3. 3. 创建了 templates/ 目录，里面是各种模板
  4. 4. 初始化了 Git 仓库

这些斜杠命令才是 Spec Kit 的灵魂——它们不是代码，而是给 AI 助手看的指令模板，告诉 AI 在每个阶段该做什么、该怎么想、该产出什么格式的东西。

四、工作流全貌：六个阶段

宪法 → 规格 → 澄清 → 计划 → 任务 → 实施

下面我逐个讲清楚每个阶段在做什么和为什么要做。

4.1 宪法（Constitution）—— 项目的"基本法"

/speckit.constitution 本项目采用 TDD、库优先架构、简洁原则。

宪法是你在开发开始前定义的不可违反的规则。比如：

  • • 所有功能必须先写测试，再写代码（TDD）
  • • 每个功能必须是独立的库，不能耦合（库优先）
  • • 项目不超过 3 个子项目（简洁原则）
  • • 直接用框架能力，不要自己包一层（反抽象）

为什么需要宪法？ 因为 AI 生成代码时容易"过度设计"——你让它写个登录，它可能给你搞一套 Repository 模式 + 工厂模式 + 策略模式。宪法就是在告诉 AI："别搞花里胡哨的，按我的规矩来。"

宪法写在 memory/constitution.md 里，后续每个阶段 AI 都会自动检查是否符合这些规则。

4.2 规格（Specify）—— 用大白话描述"做什么"

/speckit.specify 构建一个相册应用，可以按日期分组，支持拖拽排序，照片以网格方式展示。

这个命令背后发生了很多事：

  1. 1. 自动建分支：AI 会根据你的描述生成一个语义化的 Git 分支名（如 001-photo-album），并自动创建
  2. 2. 自动建目录：在 specs/001-photo-album/ 下创建规格文件
  3. 3. 生成结构化规格：AI 把你的自然语言描述转换成一份包含用户故事、功能需求、验收标准的正式文档

关键约束：规格阶段只说"做什么"和"为什么"，绝不说"怎么做"。 不能出现技术词汇。

模板里有条硬规则：

  • • ✅ 聚焦于用户需要什么、为什么需要
  • • ❌ 绝不能写怎么实现（不要提技术栈、API、代码结构）

这样做的好处是：规格说明和具体技术解耦了。今天用 React，明天换 Vue，规格不用改。

关于模糊地带的处理： AI 不会瞎猜。如果有个关键点不明确，它会用 [NEEDS CLARIFICATION] 标记出来，但最多只标记 3 个最关键的问题。剩下的会根据行业惯例做合理假设，记录在"假设"章节里。

生成完规格后，还会自动生成一份质量检查清单，逐项检查规格是否完整、无歧义、可测试。

4.3 澄清（Clarify）—— 细化和补全规格

/speckit.clarify 重点看安全性和性能方面的需求。

规格写完之后，你可以反复用 clarify 命令来补充细节。比如：

  • • "评论需要审核机制"
  • • "拖拽用原生 HTML5 API，不依赖第三方库"
  • • "启动时显示用户列表，选择后进入主页"

每澄清一次，AI 都会更新规格文档。

什么时候该用 clarify？ 当你看了生成的规格后觉得"少了点什么"或者"有个关键点需要强调"的时候。不是必须的，但强烈建议在进入计划阶段之前多澄清几轮。

4.4 计划（Plan）—— 把"做什么"翻译成"怎么做"

/speckit.plan 用 React + TypeScript + Vite，数据存 localStorage，不需要后端。

这个阶段发生了质变：从业务语言切换到了技术语言。AI 会生成：

产物内容
plan.md实施计划总纲：技术选型、项目结构、分阶段策略
research.md技术调研：每个技术选型的理由、对比了哪些方案
data-model.md数据模型：实体、字段、关系
contracts/接口契约：API 端点、事件协议
quickstart.md关键验证场景：如何快速验证核心功能

计划阶段的"门控"机制很重要：AI 会自动对照宪法检查技术方案，如果违反了规则（比如项目超过了 3 个、引入了不必要的抽象层），必须在"复杂度追踪"表里写清楚为什么不得不这样做。

这就是为什么宪法要提前定好——它在这里起了自动审查的作用。

4.5 任务（Tasks）—— 拆解成可执行的开发任务

/speckit.tasks

AI 读取计划文档，把它拆成一个个具体的开发任务：

## Phase 1: Setup
- [ ] T001: 初始化项目结构和依赖 [P]
- [ ] T002: 配置 ESLint 和 TypeScript [P]

## Phase 2: Tests (TDD)
- [ ] T003: 编写数据模型单元测试
- [ ] T004: 编写 API 契约测试

## Phase 3: Core
- [ ] T005: 实现数据模型
- [ ] T006: 实现核心业务逻辑

## Phase 4: Integration
- [ ] T007: 前后端联调
- [ ] T008: 状态管理集成

## Phase 5: Polish
- [ ] T009: 性能优化
- [ ] T010: 文档补充

[P] 标记表示这些任务可以并行执行（互不依赖）。AI 会自动分析任务之间的依赖关系。

注意执行顺序：先写测试（Phase 2），再写实现代码（Phase 3）。这是宪法里的 TDD 规则在起作用。

4.6 实施（Implement）—— AI 开始写代码

/speckit.implement

AI 按照 tasks.md 里的顺序逐个执行任务。关键行为：

  1. 1. 先检查检查清单：如果有未完成的质量检查项，会先问你"要不要继续"
  2. 2. 按阶段执行：Setup → Tests → Core → Integration → Polish
  3. 3. 遵循 TDD：先写测试、确认测试能跑（但会失败），再写实现让测试通过
  4. 4. 实时标记进度：完成的任务标记 [X]
  5. 5. 每完成一个阶段做验证：确保没跑偏

五、目录结构：理解 Spec Kit 的文件组织

初始化后的项目长这样：

my-project/
├── .specify/                    # Spec Kit 的配置中心
│   ├── integration.json         # 当前使用的 AI 助手
│   └── feature.json             # 当前活跃的功能目录
│
├── memory/
│   └── constitution.md          # 项目宪法
│
├── specs/                       # 所有功能规格（核心！）
│   └── 001-photo-album/
│       ├── spec.md              # 功能规格说明
│       ├── checklists/          # 质量检查清单
│       │   └── requirements.md
│       ├── plan.md              # 实施计划
│       ├── research.md          # 技术调研
│       ├── data-model.md        # 数据模型
│       ├── contracts/           # API 契约
│       ├── quickstart.md        # 快速验证指南
│       └── tasks.md             # 任务列表
│
├── .claude/commands/            # AI 助手的斜杠命令（以 Claude 为例）
│   ├── speckit.specify.md
│   ├── speckit.plan.md
│   ├── speckit.tasks.md
│   ├── speckit.implement.md
│   ├── speckit.clarify.md
│   ├── speckit.checklist.md
│   ├── speckit.analyze.md
│   └── speckit.constitution.md
│
└── src/                         # 源代码（AI 生成）

理解重点：specs/ 目录才是这个项目的"源代码"，src/ 是衍生品。日常维护是改 specs/ 里的文档，然后重新生成代码。

六、模板的精妙设计：怎么让 AI 不跑偏

Spec Kit 最有价值的设计其实不是 CLI 工具，而是命令模板（templates/commands/ 下的那些 .md 文件）。

这些模板是写给 AI 看的指令，里面埋了很多"约束"来防止 AI 犯常见错误：

6.1 强制分离"做什么"和"怎么做"

specify.md 模板里明确写了：

聚焦于用户需要什么（WHAT）和为什么（WHY），避免写怎么实现（HOW）

这防止 AI 在规格阶段就开始讨论技术方案。

6.2 强制标记不确定性

对不明确的地方，标记 [NEEDS CLARIFICATION: 具体问题]，不要瞎猜

AI 的常见毛病是"合理假设"——你让它做登录，它默认用邮箱+密码。模板强制 AI 在关键分歧点上标记出来让你决定，最多 3 个。

6.3 强制自检

生成规格后，自动创建质量检查清单，逐项检查

AI 写完规格后必须过一遍"自检"——有没有遗漏、有没有歧义、有没有混入技术细节。通不过就自动修复，最多修 3 轮。

6.4 宪法门控

计划阶段必须对照宪法逐条检查，违反了要写理由

这就像自动化的 Code Review，但发生在写代码之前。

七、扩展系统：给工作流加"插件"

内置扩展

# 查看可用扩展
specify extension search

# 安装 Git 扩展（自动创建分支、管理编号）
specify extension add git

扩展的 Hook 机制

扩展可以在工作流的特定节点前后插入自定义逻辑：

# .specify/extensions.yml
hooks:
  before_specify:        # 创建规格前
    - command: git-create-branch
  after_plan:            # 生成计划后
    - command: notify-team
  before_implement:      # 开始实施前
    - command: run-lint-check

每个 Hook 还可以设为 optional: true（提示用户手动执行）或 optional: false（自动强制执行）。

八、预设系统：领域模板

预设是可以叠加的模板覆盖包。比如你在做医疗项目，可以叠加一个"医疗合规"预设，它会在生成规格和计划时自动加入 HIPAA 相关的检查项。

# 搜索预设
specify preset search

# 安装预设（可以叠加，数字越小优先级越高）
specify preset add lean --priority 1

预设的组合策略有四种：replace（完全替换）、prepend（前面加）、append（后面加）、wrap（包裹原模板）。

九、30+ AI 助手支持

Spec Kit 把 AI 助手分成了几种类型：

类型命令格式代表助手
Markdown 命令.md 文件Windsurf, Roo, Cursor
TOML 命令.toml 文件Gemini, Tabnine
YAML 命令.yaml 文件Goose
Skills 技能SKILL.md 目录Claude, Codex, Devin
完全自定义自定义 setupGitHub Copilot

你可以同时安装多个 AI 助手，它们互不冲突：

specify integration install claude
specify integration install copilot
specify integration install gemini

# 切换当前使用的
specify integration use claude

十、实战：从头到尾走一遍

下面用"构建一个记账应用"作为完整示例。

第一步：初始化

specify init money-tracker --integration claude
cd money-tracker

第二步：在 Claude Code 里操作

# 1. 定规矩
/speckit.constitution 记账应用采用 TDD、简洁架构。只用 React + localStorage。不要后端。

# 2. 说需求（只说什么，不说怎么做）
/speckit.specify 一个个人记账应用，支持记录每日收支、按月份查看汇总、按类别统计饼图、导出 CSV。

# 3. 补充细节
/speckit.clarify 收支分为：餐饮、交通、娱乐、工资、其他。
支持搜索和筛选。数据存在浏览器本地。

# 4. 做技术方案
/speckit.plan React 18 + TypeScript + Vite。用 Recharts 做图表。
纯前端，localStorage 持久化。响应式设计，手机也能用。

# 5. 拆任务
/speckit.tasks

# 6. 干活
/speckit.implement

整个过程大概 15 分钟你就能得到一个结构完整、测试覆盖的记账应用。而且每个阶段你都有机会审查和调整，而不是像"随性编程"那样最后才看到结果。

十一、我的理解：Spec Kit 适合什么人

适合

  • • 经常用 AI 编程助手的人——Spec Kit 让 AI 的输出更可控、更可预测
  • • 需要多人协作的团队——规格文档天然可版本化，团队可以评审
  • • 需求经常变的项目——改规格比改代码成本低得多
  • • 想从"随性编程"进阶到"工程化"的个人开发者

不适合

  • • 一次性的小脚本——杀鸡不用牛刀
  • • 探索性编程——你连要做什么都还没想清楚的时候，先别写规格
  • • 纯后端/纯算法项目——这类项目本身就是"怎么做"比"做什么"更重要的

十二、总结

Spec Kit 的本质是三件事：

  1. 1. 结构化你的想法：通过模板和命令，强迫你（和 AI）先把需求想清楚
  2. 2. 约束 AI 的行为：通过宪法和门控，防止 AI 过度设计或跑偏
  3. 3. 自动化流程：规格 → 计划 → 任务 → 实施，每一步都有工具支持

它不是一个代码生成工具，而是一个思维框架工具。它帮你把"我想做一个 XX"这个模糊的想法，一步步变成精确的、可执行的开发计划。
