🤔 Superpowers 是什么？

想象一下，你雇了一个超级聪明但缺乏工作经验的程序员（这就是你的 AI 助手）。他很会写代码，但经常犯这样的错误：

  • ❌ 你刚说「帮我做个功能」，他就马上动手写代码——根本没搞清楚你要什么
  • ❌ 写完代码不写测试——改一个地方坏三个地方
  • ❌ 出了 Bug 就瞎猜乱改——修了一个冒出两个
  • ❌ 一个人闷头干——没有代码审查，质量没保障

Superpowers 就是给这个程序员装上一套「专业工作方法论」的系统。 装上之后，他就会自动：

先搞清楚需求
→
再制定计划
→
先写测试
→
再写代码
→
自动审查
一句话总结：Superpowers 是一套「AI 编程助手的行为规范系统」。它让你的 AI 不再是个只会埋头写代码的工具人，而是一个按专业流程做事的「超级工程师」。
重点：这些技能是自动触发的！你不需要手动调用。你的 AI 助手会根据当前场景自动判断该用哪个技能，就像有了「超能力」一样自然。

⚙️ 它是怎么工作的？

Superpowers 本质上是一套技能包（Skills）。每个技能就是一段精心设计的指令文本，告诉 AI 在特定场景下应该怎么做。它通过钩子（Hooks）自动激活——当 AI 检测到自己在做某类工作时，就会自动加载对应的技能。

技能系统的工作原理

AI 准备执行任务
→
自动检测任务类型
→
加载对应技能
→
按技能规范执行
→
高质量交付

🔄 完整工作流：从想法到交付

下面是一次完整的 Superpowers 工作流，展示每个阶段自动发生什么：

第 1 步 · 头脑风暴 自动触发

你说「帮我做个 XX」，AI 不会马上写代码，而是先问你一堆问题搞清楚需求，然后给你看设计方案。

第 2 步 · 创建工作树 自动触发

设计确认后，AI 自动创建一个独立的 Git 分支和工作空间，保护你的主分支不受影响。

第 3 步 · 写实施计划 自动触发

AI 把工作拆分成一个个 2-5 分钟的小任务，每个任务都有详细的步骤、代码和验证方式。

第 4 步 · 子代理执行 自动触发

AI 为每个小任务派出一个「子代理」去干活，干完后还有两轮审查（规格审查 + 代码质量审查）。

第 5 步 · 测试驱动 自动触发

每个任务都遵循：先写失败测试 → 确认失败 → 写最少的代码通过 → 确认通过 → 提交。

第 6 步 · 代码审查 自动触发

任务之间自动进行代码审查，发现严重问题会停止推进。

第 7 步 · 完成分支 自动触发

全部完成后，AI 验证所有测试通过，然后让你选择：合并 / 创建 PR / 保留 / 放弃。

最大亮点：AI 可以自主工作 1-2 个小时而不偏离计划！你只需要在开始时确认设计，最后检查成果就行。

📋 brainstorming — 头脑风暴

必需技能

在任何创造性工作开始前自动激活。通过对话搞清楚你到底要做什么。

它做了什么？

1

探索项目上下文

检查项目文件、文档、最近的提交记录，了解项目现状

2

一次问一个问题

不一股脑问一堆，而是逐个问题搞清楚你的需求、约束和成功标准

3

提出 2-3 个方案

带着利弊分析和推荐方案让你选择

4

分段展示设计

按复杂度分段展示设计方案，每段都问你「这样对吗？」

5

写设计文档

保存到 docs/superpowers/specs/，提交到 Git

铁律：在得到你的设计批准之前，AI 绝对不会写任何代码！即使是「做个简单的 Todo List」也要先过这关。

📝 writing-plans — 写实施计划

设计后触发

把设计方案拆解成一个个超细粒度的小任务，每个任务 2-5 分钟就能完成。

计划的粒度有多细？

每个任务被拆成这样的步骤：

  1. 写失败测试
  2. 运行确认它失败了
  3. 写最少的代码让它通过
  4. 运行确认它通过了
  5. 提交

计划文档长什么样？

🌳 using-git-worktrees — Git 工作树

开发前触发

在开始写代码前，自动创建一个隔离的工作空间，保护你的主分支。

通俗理解

就像你在办公室有自己的工位。Superpowers 会自动给你开一个独立的工位，这样你做的任何修改都不会影响到公共区域（主分支）。做完后再把成果合并回去。

工作流程

1

检测是否已有隔离空间

先检查你当前是不是已经在独立工位里了，避免重复创建

2

创建工作树

如果没有，就用平台原生工具或 Git 命令创建一个新分支的工作树

3

安装依赖

自动检测项目类型（Node/Rust/Python/Go）并安装依赖

4

验证测试基线

运行测试确保起点是干净的，后续出了问题能分清是新引入的还是旧的

👷 subagent-driven-development — 子代理驱动开发

核心执行引擎

为每个任务派出一个全新的「子代理」，完成后进行两轮审查。这是 Superpowers 的核心执行引擎。

通俗理解

想象你是一个项目经理（主代理）。你不会自己去写每一行代码，而是：

  1. 派一个程序员（实现子代理）去做任务
  2. 派一个质检员（规格审查子代理）检查是否按需求做的
  3. 再派一个高级工程师（代码质量审查子代理）检查代码写得好不好
  4. 都通过了才进入下一个任务

每个任务的处理流程

📝 提取任务
→
👷 派实现代理
→
📋 规格审查
→
🔍 质量审查
→
✅ 完成
为什么用子代理？ 每个子代理都是全新的，没有之前任务的上下文污染。这样它只会专注于当前任务，不会被之前的信息干扰。而且审查是独立的第三方，更客观。

模型选择策略

任务类型模型选择举例
机械性实现（1-2 个文件，规格清晰）便宜快速的模型写一个简单的工具函数
集成性任务（多文件协调）标准模型实现 API 接口集成
架构/设计/审查任务最强大的模型审查整体代码质量

🧪 test-driven-development — 测试驱动开发（TDD）

铁律

红-绿-重构循环：先写失败测试，再写最少代码通过，最后重构。没有例外。

TDD 三步循环

🔴 RED — 写失败测试

写一个测试来描述你期望的行为。运行它，确认它确实失败了。

// 测试：重试操作 3 次
test('重试失败操作 3 次', async () => {
  let attempts = 0;
  const operation = () => {
    attempts++;
    if (attempts < 3) throw new Error('fail');
    return 'success';
  };
  const result = await retryOperation(operation);
  expect(result).toBe('success');
  expect(attempts).toBe(3);
});

🟢 GREEN — 写最少代码通过

只写让测试通过的最少代码。不多不少。

async function retryOperation<T>(fn: () => Promise<T>): Promise<T> {
  for (let i = 0; i < 3; i++) {
    try { return await fn(); }
    catch (e) { if (i === 2) throw e; }
  }
  throw new Error('unreachable');
}

🔵 REFACTOR — 重构清理

测试通过后，清理代码：去重、改善命名、提取公共方法。确保测试仍然通过。

铁律：如果你先写了代码再补测试，删掉代码重新来！
「先写代码再补测试」不是 TDD。测试后写能通过 = 什么都没证明。只有看到测试先失败再通过，才能证明测试真的在测正确的东西。

🔍 systematic-debugging — 系统化调试

遇 Bug 触发

遇到 Bug 时不瞎猜，而是按照四阶段流程找到根因再修。

四阶段调试流程

阶段 1：根因调查

  • 仔细读错误信息——错误信息里往往藏着答案
  • 稳定复现——能每次都触发吗？
  • 检查最近的变更——什么改动可能导致？
  • 追踪数据流——坏的值是从哪来的？

阶段 2：模式分析

  • 找类似的正常工作的代码
  • 对比正常和异常的差异
  • 列出每一个不同点，不管多小

阶段 3：假设验证

  • 提出一个明确的假设：「我认为原因是 X，因为 Y」
  • 做最小的改动来验证
  • 一次只改一个变量

阶段 4：实施修复

  • 先写一个能复现 Bug 的失败测试
  • 修根因，不修症状
  • 验证测试通过
  • 如果修了 3 次还没好 → 停下来质疑架构设计
实测数据：系统化调试平均 15-30 分钟修好，随机瞎改平均 2-3 小时。首次修复率 95% vs 40%。

👀 requesting-code-review — 代码审查

任务之间触发

每完成一个任务就自动进行代码审查，按严重程度报告问题。严重问题会阻止继续推进。

在子代理驱动开发中，审查分两轮：

审查轮次审查什么谁来审
第一轮：规格审查代码是否完全按照规格要求实现？有没有多做或少做？规格审查子代理
第二轮：质量审查代码质量如何？有没有坏味道、安全隐患、性能问题？代码质量审查子代理

🎉 finishing-a-development-branch — 完成开发分支

收工触发

所有任务完成后，验证测试、提供选项、清理工作空间。

完成后给你 4 个选项

🔀

1. 本地合并

合并回主分支，清理工作树

📨

2. 创建 PR

推送分支，创建 Pull Request

📦

3. 先保留

保留分支和工作树，你自己处理

🗑️

4. 放弃

删除所有改动（需二次确认）

🧠 核心理念

🧪

测试先行

永远先写测试再写代码。没有例外。

📐

系统化 > 随意

靠流程不靠猜测。系统化方法永远比拍脑袋快。

✂️

减少复杂度

简单是首要目标。YAGNI（你不会需要它）原则贯穿始终。

🔬

证据 > 声称

验证后才算完成。看到测试先失败再通过才算数。

关键原则解读

原则英文通俗理解
YAGNIYou Aren't Gonna Need It别提前加功能。现在用不到就别写。
DRYDon't Repeat Yourself别重复写同样的代码。提取公共方法。
TDDTest-Driven Development先出考题再写答案。测试驱动设计。
红-绿-重构Red-Green-Refactor失败→通过→清理。每个功能都走这个循环。

❓ 常见问题

Q1：Superpowers 免费吗？

是的，Superpowers 完全免费开源（MIT 协议）。但你需要为使用的 AI 工具（Claude Code、Cursor 等）付费。

Q2：它会消耗更多 Token 吗？

是的，因为子代理开发会增加 API 调用次数（每个任务有实现 + 规格审查 + 质量审查三轮）。但这换来的是更高的代码质量和更少的 Bug，总体上反而省钱省时间。

Q3：我可以只用部分技能吗？

Superpowers 的技能是自动触发的，不需要手动选择。每个技能在特定场景自动激活。如果你想禁用某个技能，需要修改配置。

Q4：支持哪些编程语言？

Superpowers 不绑定特定编程语言。它的方法论（TDD、系统化调试、代码审查等）适用于所有语言。

Q5：安装后需要做什么配置吗？

安装后不需要额外配置。Superpowers 通过 Hook 机制在会话启动时自动加载。你只需要像平时一样使用你的 AI 工具就行。

Q6：谁创建了 Superpowers？

Superpowers 由 Jesse Vincent 和 Prime Radiant 团队创建。Jesse 是一位知名的开源开发者。

Q7：可以在公司项目中使用吗？

可以。MIT 协议允许在任何项目中免费使用，包括商业项目。项目还有社区 Discord 提供支持。
